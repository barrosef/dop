# `dop-app` — the current state (an analysis)

> **Date:** 2026-08-29
> **Base analysed:** the `dev` branch, commit `ef9a3de` ("Validate multi-repository commit attribution")
> **Method:** a reading of the code, the history, the import graph and the versioned screenshots
> **Purpose:** input for the restructuring round

## Summary

`dop-app` **has stopped being a frontend**. Today it is a **pnpm monorepo** with a frontend, an
HTTP server, a PTY terminal server, a database, an OpenAPI contract and a codegen pipeline. The
product was renamed in the interface to **"DOP IDE"** and reorganized around a **single cockpit
per workspace**, in place of the PRD's screen-by-screen navigation.

Three findings require a decision before anything else:

1. **The meta-repository points at the wrong place.** The submodule is pinned at `ad15b82` of
   `main` — a 1-commit scaffold. All the real work is on `dev`, which **has no common ancestor
   with `main`**. The two histories are independent.
2. **3,523 lines are orphaned.** The 7-stage execution screen, built over adjustment prompts
   05–17, **is no longer reachable from the application**. The restructuring to a cockpit
   changed the routing and did not re-anchor the screen.
3. **`dop-app` grew a backend inside it.** There is an Express server with a PTY terminal
   running in there. That collides head-on with the `dop-core` (a gRPC core) + `dop-api` (a BFF)
   architecture decided in the previous conversation.

## 2. What the repository is today

A pnpm monorepo (Node 24, TypeScript 5.9), organized into `artifacts/` (applications) and
`lib/` (shared packages):

```
artifacts/
├── dop/               a React 19 + Vite 7 + Tailwind 4 + shadcn frontend   (97 files)
├── api-server/        Express 5 + pino + WebSocket + node-pty              (13 files)
└── mockup-sandbox/    a mockup preview sandbox                             (69 files)
lib/
├── api-spec/          OpenAPI 3.1 + Orval (codegen)
├── api-zod/           generated Zod schemas + the commit attribution rule
├── api-client-react/  a generated react-query client
└── db/                Drizzle + PostgreSQL
scripts/               the workspace's utilities
```

### 2.1 What is substance and what is scaffolding

An important distinction, because the volume deceives:

**Scaffolding from the Replit template, with no product content:**
- `lib/api-spec/openapi.yaml` — it declares **a single endpoint**, `GET /healthz`.
- `lib/db/src/schema/index.ts` — **no table**; only the example comment and `export {}`.
- `lib/api-zod` and `lib/api-client-react` — generated from the OpenAPI above, so they contain
  only `HealthStatus`.
- `replit.md` — an unfilled template, still with `# [Project name]` and "_Populate as you
  build_" sections.

**Real own code in the backend — only two files:**
- `artifacts/api-server/src/lib/terminal-server.ts` (270 lines) — a terminal server over
  WebSocket + `node-pty`, with a limit of 4 sessions, a 20-minute idle timeout, a 16 KB ceiling
  per input, identifier validation and the PTY confined to a root (`DOP_TERMINAL_ROOT`).
- `lib/api-zod/src/repository-commit-attribution.ts` (58 lines) — a domain rule, see §4.

That is: **`dop-app`'s backend implements nothing of DOP**. All the product logic lives in the
frontend, fed by `mockClient.ts`.

### 2.2 A consequence: the codegen pipeline is disconnected

The product's real contract is in `artifacts/dop/src/lib/api/types.ts` (hand-written
TypeScript). The `openapi.yaml` does not describe it. So the client generated by Orval **is not
used** for DOP data — the frontend consumes `mockClient` directly. The codegen infrastructure
exists and is empty.

## 3. The restructuring into an IDE

The document `attached_assets/Pasted-Chat-vamos-reestruturar-...txt` records the instruction that
originated the turn. Six points, and the third is the thesis:

> "Let's think more like an IDE, the platform is a development environment, it is not a system.
> So the focus always has to be on development and on the activities related to the dev and to
> what a developer needs to know."

What was actually implemented from that instruction:

| Instruction | State |
|---|---|
| "demands" → **cards**, with dynamic types coming from the provider | ✅ `Card`, `cardTypes: string[]` per workspace; `Demand` kept as an alias |
| The detailed view **starts at the workspace**, the card becomes a filter | ✅ A single `/workspaces/:id` route; the selected card becomes `?card=`; the old routes redirect |
| Centralize branches and PRs **inside repositories** | ✅ A `repo → overview / branches / PRs` tree, with a `NodeKind` and level-by-level navigation |
| Get rid of the separate branches/PRs panel | ✅ The cockpit's sections: `overview`, `chat`, `repos`, `infra` |
| i18n `en` + `pt-BR` | ✅ `i18n.ts`, ~430 keys in both languages |
| "Dossier" → the correct technical expression | ✅ `DemandDossier` → **`RepositoryOverview`** |

Beyond what was asked, two IDE capabilities appeared that were in no earlier document:

- **A real interactive terminal** — `infra-terminal.tsx` in the frontend against the
  `api-server`'s PTY. It is not a simulated log: it is a shell.
- **A runtime scoped per card** — `RuntimeApp.taskId` and `RuntimeService.taskIds` let the same
  application run on different ports for different cards (in the mocks: `portal-backend` on
  ports 8080, 8083 and 8084 for cards d-1, d-3 and d-4). That is the behaviour of a parallel
  development environment, not of a dashboard.

## 4. The contract evolved well beyond the PRD

`types.ts` and `client.ts` diverged substantially from the preliminary `DopApi` of the Replit
prompt. The changes confirm, in code, several of the tensions raised in the analysis of the 20
adjustment prompts.

### 4.1 A git provider per repository — confirmed

```ts
type GitProvider = 'azure_devops' | 'github' | 'gitlab' | 'gitlab_self_hosted' | 'bitbucket';
interface RepoConfig { provider?: GitProvider; ... }   // per REPO
interface Workspace  { gitProvider?: GitProvider; ... } // now optional
```

The workspace's `gitProvider` became optional and the provider moved to the repository — and the
mocks already exercise it: the "Payments API" workspace has repositories on Azure DevOps **and**
GitLab at the same time. **Bitbucket** appeared, present in no document.

### 4.2 A plural task manager — earlier than foreseen

```ts
interface TaskManagerConfig { provider: 'jira' | 'clickup' | 'redmine' | 'custom'; ... }
```

The PRD put ClickUp and others explicitly **out of 1.0's scope**. The interface already assumes
them, and the mocks already use ClickUp.

### 4.3 New types that did not exist

| Type | Origin | What it carries |
|---|---|---|
| `ExecTask` | prompt 06 | `parallelGroup: number` — parallelism between repositories as first-class data |
| `ExecFile` | prompt 06.3 | a unified `diff`, `linesAdded`/`linesRemoved`, `error` |
| `TestPlan` | prompt 11 | a `unit` and `e2e` test plan in Markdown |
| `Reviewer` | prompt 13.5 | `status: 'approved' \| 'rejected' \| 'pending'` per reviewer |
| `RuntimeService` | prompt 03.2 | infrastructure scoped per card |
| `RepositoryOverview` | the restructuring chat | it replaces `DemandDossier` |

And the existing ones gained substance: `Stage` now has `document`, `execData` and `testPlan`;
`FileTouched` gained `gitStatus`, `repo`, `branch`, `diff` and line counts; `PullRequest` gained
`reviewers[]`.

### 4.4 A genuine domain rule, discovered through the UI

`repository-commit-attribution.ts` is the repository's most interesting find. It is the only
real business logic written, and it was born of a problem that only appears when you try to
display the data:

> A card that touches **several repositories** cannot reuse an aggregate commit total as if it
> were a single repository's. Either there is a count for **every** repository, or the
> attribution is declared **unavailable**. And, where there is attribution, the aggregate has to
> match the sum.

The Zod schema refuses a payload that violates it, and the frontend validates **every** card
payload at the boundary (`validateCard`). It is a rule the platform has to honour on the server
side — and it is exactly the kind of thing that appears when the screen is built before the API.

### 4.5 What the interface gained

```ts
listAllCards(): Promise<Card[]>                        // a cross-workspace query
streamLogs(cardId, source, filter?: { testType, testRepo })   // selective logs
```

`listAllCards` is the embryo of requirement R2.9 ("where I am needed", a cross-project view).
The filter in `streamLogs` serves prompts 07.1 and 12.

### 4.6 What the 20 prompts asked for and the interface still does not have

- Creating and listing remote repositories at the provider (prompts 14, 18, 20).
- CRUD and versioning of the Markdown artifacts — today `Stage.document` is a read-only string,
  with no write path (prompts 05, 11).
- A human validation checklist (prompts 12, 16).
- An observable finalization process (prompt 17).
- Custom configuration per card and composing repositories per card (the first line of the
  prompts file + prompt 14).

## 7. What this means for the platform

Three readings that matter for the restructuring:

**The UI discovered requirements the documents did not have.** The commit attribution rule, the
runtime scoped per card, parallelism as data (`parallelGroup`), the provider per repository —
none of that was in the PRD, and all of it appeared while building the screen. Today's
`types.ts` is a more current source of requirements than PRD 1.0.

**The IDE thesis matches the decided architecture, and reinforces it.** An interactive terminal,
a parallel runtime per card, navigation through a repository tree — these are development
environment capabilities, and they all depend on bidirectional streaming and shared state. They
justify the gRPC core and the streaming BFF better than the original PRD did.

**The stage model became orphaned right when autonomy comes up.** The 3,523 idle lines
implement a 7-stage flow with a strong dependency on human intervention — precisely what the new
direction wants to revise in favour of autonomy. The code became unreachable before the decision
was taken. Re-anchoring without rethinking would be restoring the old model out of inertia.
