# ADR-0021 — The project's knowledge is a git repository, hosted by the platform

- **Status:** Accepted
- **Date:** 2026-09-03
- **Relations:** gives ADR-0006's layers their storage; moves ADR-0017's knowledge boundary to the project; relies on ADR-0001, ADR-0003 (commit attribution — not restated here), ADR-0004, ADR-0009

## Context

Every document that is the agent's knowledge — rules, maps, memories,
demand specs and plans — must be present in every sandbox of a project
from provisioning, writable by agents, shared between demands, and
attributed per change.

## Decision

1. **Every project has a root repository**, created with the project in a
   git server the platform runs. Layout:
   ```
   README.md      generated manifest: contents, sizes, reading order
   rules/         what the agent obeys
   index/         one map per repository of the project
   memory/        findings and lessons from past demands
   demand/<id>/   spec.md, plan.md, context.md … of one demand
   ```
   `README.md` is regenerated by the platform on every push.
2. **Every sandbox of the project clones it** at `/project`, read-write.
   Agents read files and write with `git commit` + `git push`; sharing
   between demands is push/pull; a conflict the agent cannot resolve is an
   attention item.
3. **The sandbox's credential** is a per-demand, short-lived token scoped
   to that project's root repository, read-write, delivered as a projected
   file (never an environment variable). It is the only credential in the
   sandbox.
4. **A user's remote is a push mirror:** the platform's repository is the
   primary; the platform pushes onward with the user's credential from the
   vault. No two-way sync in v1. A person may clone the platform's
   repository directly with their platform identity.
5. **Every push is an event** (author, paths, commit): it regenerates the
   manifest, feeds the timeline, and — for commits into `memory/` — closes
   the lessons loop.
6. **Port:**
   ```go
   type ProjectRepository interface {
       Ensure(ctx, projectID) (CloneURL, error)
       IssueToken(ctx, projectID, demandID string, ttl time.Duration) (Token, error)
       Commit(ctx, projectID string, files []File, author Author, message string) (Commit, error)
       Read(ctx, projectID, path string) ([]byte, error)
       SetMirror(ctx, projectID, remoteURL string, credential SecretRef) error
   }
   ```
   Two adapters: the platform's git server on Kubernetes; bare repositories
   behind `git http-backend` locally. One contract suite.
7. **Text in git, bytes in the `ObjectStore`.** Large binaries are
   referenced from the repository, not stored in it.
8. **Sandbox contract guarantees:** the knowledge path is readable,
   writable, visible to the next sandbox of the project after a push,
   persistent across resume and demands, fenced per project (a sandbox of
   project X cannot open project Y's repository); the mirror's credential
   is never in a sandbox.

## Alternatives considered

- **A ConfigMap** — rejected: 1 MiB, etcd, configuration not data.
- **A per-demand volume filled by a loader** — rejected: per demand,
  read-only, no sharing.
- **A read-write-many volume per project** — rejected: unavailable locally;
  no attribution.
- **Object storage mounted as a filesystem** — rejected for text:
  last-writer-wins, no authorship; kept for binaries.
- **The user's provider as the primary** — rejected: requires an integration
  before knowledge exists; the user's credential in the sandbox's path.

## Consequences

- A stateful git server in `dop-infra`, with storage and backup.
- `git` in the devbox image; a clone at provisioning.
- The code repositories still come from the user's provider; the sandbox
  mechanism here is the one they will use if the platform ever fronts them.
