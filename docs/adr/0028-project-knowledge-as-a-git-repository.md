# ADR-0028 — The project's knowledge is a git repository, hosted by the platform

- **Status:** Accepted
- **Date:** 2026-09-03
- **Refines:** [ADR-0009](0009-context-as-subsystem.md) (the three layers get a home on disk), [ADR-0024](0024-sandbox-per-demand.md) (the knowledge boundary moves up to the project; the workspace boundary stays)
- **Depends on:** [ADR-0001](0001-infrastructure-behind-ports.md) (two adapters and a contract suite), [ADR-0003](0003-organization-credential-human-authorship.md) (**every rule about commits, authorship and push lives there** — this ADR only references it), [ADR-0006](0006-demand-as-event-log.md) (a push is an event), [ADR-0013](0013-resource-as-unit-of-sharing.md) (a repository is a resource)
- **Scope:** HOW the project's knowledge is structured and shared. Not how a commit is attributed or pushed — that is ADR-0003's, for this repository as for any other.

## Context

The owner's expectation, stated on 2026-09-03: *every document that serves as
the agent's knowledge base — memories, context, specs, plans — is available to
ANY demand of the project the moment the microVM and the agents come up. No
sends, no requests, no ConfigMaps. From the agent's point of view the content
simply exists. The knowledge is SHARED and COLLABORATED between agents:
transparent, practical, accessible, available and secure.*

Two attempts preceded this decision, and both were the wrong kind:

1. **A ConfigMap projected as a volume** — config, not data; lives in etcd; caps
   at 1 MiB. Rejected by the owner on sight.
2. **A per-demand PersistentVolume filled by a loader pod pushing a tar over
   WebSocket stdin, mounted read-only.** A transport, per demand, read-only,
   rewritten at every resume — the opposite of shared and collaborated.

A per-project volume, the obvious next step, fails on two facts: the local
cluster refuses `ReadWriteMany` (*"NodePath only supports ReadWriteOnce"*), and
a shared filesystem has no idea WHO changed a file — which is the one thing
ADR-0006 requires this platform to always know.

The owner then named the answer: **versioned in git**. Instead of sharing a
volume, share a repository.

## Decision

### 1. The knowledge lives in the project's ROOT repository

Every project has a root repository. It is born with the project, **under the
hood, in a git server the platform runs** — the user does not integrate it and
does not create it. Rules, repository maps, memories, and the demands' specs,
plans and context are files in it, in the layout `knowledge/library.go` already
defines:

```
README.md          the manifest: what is here, sizes, what to read first
rules/             what the agent OBEYS
index/             one map per repository of the project
memory/            findings and lessons from past demands
demand/<id>/       spec.md, plan.md, context.md … of one demand
```

`README.md` is **generated by the platform** on every push. It is not a file
somebody maintains: a manifest that drifts from the tree is worse than none.

### 2. Every sandbox of the project clones it; agents write by committing

At provisioning, the root repository is cloned into the sandbox at
`SandboxDocumentsPath` (`/project`) — the constant survives, its meaning
changes: it is a **working copy**, read-write. Agents read with the tools they
already have and write with `git commit` + `git push`. Sharing between demands
is push/pull; a conflict is git's conflict, resolved by git's rules, and one
the agent cannot resolve becomes an attention item.

How a commit is attributed — `author`, `committer`, what the push uses — is
**ADR-0003's rule and is not repeated here**. What this ADR relies on is only
the consequence: a repository's history is an attribution trail, which is why
history and rollback come free where a volume gave none of them.

### 3. The sandbox authenticates with a token that opens exactly one repository

The platform's git server is inside the cluster. At provisioning the core mints
a **per-demand, short-lived token**, scoped to that project's root repository,
read-write, expiring with the sandbox. It reaches the sandbox **as a projected
file** — the shape the execution substrate spec §5 already fixes for derived
tokens — never as an environment variable, which every child process inherits.
It is the only credential the sandbox holds.

This is the one place a credential enters the sandbox, and the reason it is
acceptable is what the token opens: **the agent's own workbench**, which the
agent is supposed to write to anyway. It is not a third party's key. It cannot
reach another project. It cannot reach the user's remote. It dies with the
demand. The alternative — authenticating the sandbox by its network identity —
is weaker (spoofable inside the cluster) and harder to audit.

### 4. The user's remote is a MIRROR, attachable at any time

A user may point the project at a remote of their own — GitHub, GitLab — at any
moment. When they do, **the platform's repository stays the primary** and the
user's remote becomes a **push mirror**: every push to the platform is pushed
onward by the platform, with the user's credential from the vault (ADR-0022).
The sandbox never sees that credential.

There is **no two-way sync in v1**. Two-way sync of a repository two parties
write to is a conflict engine; nobody asked for one. Whoever wants to edit
knowledge by hand has two doors that need no sync: the cockpit (which commits
through the core) and **cloning the platform's repository directly** — it is a
real git server, and a person authenticates to it with their platform identity.
Moving the primary to the user's remote is a one-time migration, not a mode.

### 5. Every push is an event

The git server's post-receive reaches the core: a push becomes an event
(ADR-0006) carrying the author, the paths and the commit. It is what fires the
`README.md` regeneration, what feeds the timeline, and — when an agent commits
into `memory/` at the end of a demand — what makes the lessons loop (P-41)
exist: a demand's findings become the project's memory by the agent writing
them where the next agent will read them.

### 6. The port

```go
// ProjectRepository is the home of a project's knowledge — a git repository
// the platform hosts.
type ProjectRepository interface {
    // Ensure creates the repository if absent. Idempotent by project.
    Ensure(ctx, projectID) (CloneURL, error)
    // IssueToken mints the sandbox's credential: one project, read-write,
    // a TTL. The token is the demand's identity to git.
    IssueToken(ctx, projectID, demandID string, ttl time.Duration) (Token, error)
    // Commit writes files on the platform's behalf — rules from the cockpit,
    // the regenerated README. Attribution follows ADR-0003.
    Commit(ctx, projectID string, files []File, author Author, message string) (Commit, error)
    Read(ctx, projectID, path string) ([]byte, error)
    // SetMirror attaches the user's remote. Direction: platform → remote.
    SetMirror(ctx, projectID, remoteURL string, credential SecretRef) error
}
```

Two adapters from day one, per ADR-0001: the platform's git server on
Kubernetes, and a local one (bare repositories on disk behind `git
http-backend`) for the laptop — the same contract suite runs against both.

### 7. What this decides for the code repositories too (P-38)

The plumbing is shared: `git` in the devbox image, a clone at provisioning, a
credential that opens one thing. The code repositories still come from the
user's provider and are out of this ADR's scope — but the day the platform's
git server fronts them as a proxy, the sandbox-side mechanism is already the
one described here.

## Alternatives considered

**An RWX PersistentVolume per project.** The local storage class refuses it;
Filestore/CephFS/NFS would provide it; and it would still have no attribution.
Git has attribution built in. Rejected.

**Object storage mounted as a filesystem (GCS FUSE, Firebase Storage).** Zero
copies — the storage IS the volume — and it is the storage the platform already
uses. But no CSI driver on k3d or OKD, last-writer-wins semantics, and
versioning that gives history without authorship. Rejected for v1; it remains
the right shape for large binary artefacts (diagrams, reports), which a git
repository is bad at.

**The user's own provider as the primary.** It requires the user to integrate a
provider BEFORE the project can hold knowledge, which contradicts "born under
the hood". It also puts the user's credential in the sandbox's path. Rejected —
it survives as the mirror.

**A ConfigMap.** 1 MiB, etcd. Rejected.

## Consequences

- **A stateful component to run:** a git server, with storage and backup, in
  `dop-infra`. It is the price of "born under the hood", and the platform
  already runs Postgres and NATS the same way.
- **`git` enters the devbox image**, along with the clone at provisioning — the
  half of P-38 this ADR settles.
- **The contract's guarantees 18–21 are rewritten:** 18 stays (readable at the
  path), 19 flips (writable, and a push is visible to the next sandbox of the
  project), 20 flips (persists across resume and across demands — it is a
  repository), 21 stays (paths that escape are refused). New: a sandbox of
  project X cannot open project Y's repository, and the mirror's credential is
  never in a sandbox.
- **The mechanism built on 2026-09-02/03 is removed** — the loader pod, the
  stdin push, the read-only mount. `SandboxSpec.Documents` gives way to the
  clone URL and the token.
- **P-39 (RWX) and P-40 (attribution) dissolve.** P-41 (the lessons loop) gains
  its mechanism.
- **Large binaries do not belong here.** A git repository is the wrong home for
  a 40 MB diagram export; those stay in the ObjectStore with a reference in the
  repository. The rule: text in git, bytes in the bucket.
